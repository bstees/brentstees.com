The most useful new signal this week is that the industry is getting more concrete about **learning from agent failures** rather than merely adding more instructions. Three of this week's items fit together particularly well.

### 1. AgentGuard turns previous agent failures into conditional guardrails

**AgentGuard**, published September 14, analyzed 642 documented failure trajectories from coding agents: changing unrelated files, rewriting tests, ignoring failed validation, unsafe commands, and similar behaviors. It extracts recurring failure patterns and converts them into rules that activate only when relevant to the current task.

The numbers are substantial: using the same Claude Code/Haiku 4.5 agent, abnormal executions fell from **69.0% to 26.7%**, while successful completion increased from **21.7% to 35.0%**.

**Source:** [AgentGuard: Learning Execution Guardrails from Anomalous Coding-Agent Trajectories](https://arxiv.org/abs/2609.16287)

**Why it matters:** This provides empirical support for something more sophisticated than a giant `AGENTS.md`: the harness can accumulate organizational experience from mistakes without burdening every task with every rule.

**Practical takeaway:** Add a **failure-promotion loop** to your framework:

**human intervention → classify why intervention was necessary → reusable guardrail → regression scenario**

Don't automatically promote every correction. Promote recurring, generalizable failure modes.

### 2. We now have evidence that the agent harness itself is becoming a software supply chain

**Scanning the Harness**, released September 7 and worth including this week because of its direct operational relevance, examined **3,171 public GitHub repositories** containing coding-agent configurations: skills, hooks, MCP declarations, instruction files and subagents.

The researchers found confirmed security defects in **16.0%** of configurations. Examples included unpinned MCP servers, apparently scoped permissions that actually permitted arbitrary execution, and reusable skills granting shell access to whoever installed them.

**Source:** [Scanning the Harness, version 1](https://arxiv.org/abs/2609.07360v1). A later revision changed the title and category rates; this archive preserves the version and 16.0% result available for the original brief.

**Why it matters:** Skills and MCP servers are starting to resemble dependencies, but we largely manage them like configuration snippets. There is usually no equivalent of a package lockfile, dependency scanner or meaningful permission manifest.

**Practical takeaway:** Treat your agent environment like production dependencies. Pin MCP versions where possible, review third-party skills, explicitly enumerate permissions, and put agent configuration under code review. I'd also add automated harness scanning to CI as the tooling matures.

This is especially relevant to your Level-3 architecture: **the harness itself now belongs inside your threat model.**

### 3. RAG research shows why retrieving *knowledge about failures* can beat retrieving similar code

A new ACM TOSEM paper published September 16, **vul-rag**, examined vulnerability detection and found an uncomfortable baseline result: LLMs were extremely poor at distinguishing vulnerable code from closely related patched-but-benign code, with accuracy reported between **0.06 and 0.14** in that setting.

The researchers instead retrieve multidimensional knowledge distilled from historical vulnerabilities and fixes, giving the model information about **why** a pattern was vulnerable rather than simply finding semantically similar source.

[Read the ACM paper](https://doi.org/10.1145/3797277)

**Why it matters:** This is a useful lesson for engineering RAG generally. Similarity isn't necessarily the thing an engineering agent needs. Sometimes it needs precedent, causality, constraints or previous failure knowledge.

**Practical takeaway:** I'd split an engineering knowledge layer into distinct retrieval intents:

**Code navigation** → symbols/search/dependencies
**Architecture** → relationships/design decisions
**Precedent** → previous PRs/tickets
**Failure knowledge** → incidents/bugs/security findings
**Policy** → engineering and security constraints

Then let the agent retrieve according to *why it needs context*, rather than funneling everything through one vector index.

### 4. 1Password published unusually concrete production numbers for agent-assisted delivery

[1Password's engineering case study](https://openai.com/index/1password/), published September 8, reports a **20.9% productivity improvement**, **10.9% reduction in median PR cycle time**, and a production investigation spanning more than ten microservices dropping from roughly two hours to **5–20 minutes** after integrating Codex across planning, implementation, review, testing and incident investigation. These are company-reported results, so I would treat them as useful field evidence rather than controlled research.

More interesting than the headline numbers is their architecture. 1Password gives agents significant freedom **inside defined engineering/security boundaries**, puts AppSec policies into reusable skills, and passes secret *references* to agents rather than putting plaintext credentials into model context.

**Why it matters:** This is one of the better examples I've seen of autonomy being expanded because the surrounding system has become stronger, rather than because someone simply decided to trust the model more.

**Practical takeaway:** Measure your AI rollout against delivery outcomes you already care about:

**cycle time, escaped defects, rework, failed changes, MTTR and human intervention rate.**

Agent usage, tokens and AI-authored LOC are operational telemetry, not success metrics.

### 5. Anthropic's internal usage provides a useful reality check on “autonomy”

Anthropic disclosed this week that Claude now **leads roughly 26% of its AI R&D work**, up from under 1% in February, while AI collaborates with humans or leads on more than 90% of the work measured. Crucially, Anthropic says it still measured **no area as fully autonomous**.

Their earlier internal study also found employees reporting Claude use in roughly 59–60% of their work while saying only **0–20% could generally be fully delegated**; supervision and validation remained common, particularly for consequential work.

**Sources:** [Measurements for understanding the pace of AI development inside frontier labs](https://www.anthropic.com/institute/measuring-pace-of-ai-development) and [How AI is transforming work at Anthropic](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)

**Why it matters:** Heavy agent usage and high autonomy are not synonymous. One of the world's most AI-native engineering environments appears to be moving toward pervasive **collaboration plus selective delegation**, rather than simply removing engineers from the loop.

**Practical takeaway:** Track two different metrics in an agentic SDLC:

**AI participation:** How much work involves an agent?
**Human intervention:** Where and *why* did a human need to exercise judgment?

The second metric is particularly valuable because it tells you where the harness should improve next.

### The idea I'd steal this week

AgentGuard changes one piece of how I'd structure your framework.

Instead of thinking only in terms of:

**agent work → human judgment → continue**

I'd make the complete lifecycle:

**agent work → automated evidence → human judgment when necessary → capture reason for intervention → decide whether that reason can become a guardrail/test/skill → next run**

That last step closes the learning loop.

Over time, the goal isn't simply **fewer human checkpoints**. It's fewer instances where a human has to make **the same judgment twice**.

That is a much more defensible path toward increasing agent autonomy: human judgment progressively gets converted into executable organizational knowledge, while genuinely novel judgment stays human.
