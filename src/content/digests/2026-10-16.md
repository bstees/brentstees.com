**This week's theme: Agentic software engineering is moving toward independently verifiable execution, persistent project state, and testing that reflects actual user behavior.**

Five developments stood out, particularly from this week's Automated Software Engineering (ASE 2026) conference and newly published research.

## 1. Doc2Harness: Benchmarking the engineering system around an agent

**October 14 | New research**

[Read: Doc2Harness — Benchmarking Long-Horizon Harness Engineering](https://arxiv.org/abs/2610.20344)

**What changed:** Doc2Harness introduces a deterministic benchmark for evaluating an AI model's ability to build a complete coding-agent harness.

Researchers evaluated 19 frontier models against 328 behavioral tests. The strongest achieved **53.05%**, meaning even the best model failed nearly half the tests.

Importantly, tests examine observable behavior: model requests, filesystem changes, process exits, and command output.

**Why it matters:** This establishes harness engineering as something that can be tested independently of the software an agent produces.

**Practical takeaway:** Build a behavioral regression suite for an agent framework. Test permissions, tool execution, state persistence, error recovery, and approval gates using scripted model responses rather than relying exclusively on live-model evaluations.

## 2. Interaction-as-a-Judge: Testing the UI like a human beats inspecting code

**October 13 | New research**

[Read: Interaction-as-a-Judge](https://arxiv.org/abs/2610.17895)

**What changed:** Researchers evaluated computer-use agents that interact directly with applications rather than judging generated code or screenshots alone.

Their approach improved:

- Human-preference prediction from **65.6% to 69.1%**
- Requirement verification from **77.0% to 81.6%**
- Repair of broken requirements within five attempts from **55.4% to 75.5%**, compared with code-only feedback.

**Why it matters:** A React application can pass unit tests while remaining functionally incorrect from the user's perspective.

Interactive verification catches problems that static inspection cannot reliably identify.

**Practical takeaway:** Extend browser-based verification beyond scripted assertions.

Give an independent agent a user-facing acceptance criterion, let it interact with the running application, and compare its findings against deterministic tests.

For interaction-heavy web applications, this approach can catch layout, navigation, responsiveness, and interaction problems that conventional unit tests miss.

## 3. StateHarness: Persistent project knowledge improves long-running coding agents

**October 13 | New research**

[Read: StateHarness — Maintaining Evolving Project State](https://arxiv.org/abs/2610.17616)

**What changed:** StateHarness maintains structured knowledge about the agent's current problem, hypotheses, architectural relationships, modifications, and unresolved work.

Rather than relying on an expanding conversation history, it continuously updates a compact project-state representation.

Reported results include:

- RefactorBench full-chain completion improving from **29.4% to 35.3%**
- Cleanup-check accuracy increasing from **87.0% to 95.4%**
- Reduced residual technical debt on ChainSWE, although some regressions increased.

**Why it matters:** Long-running agents frequently lose track of earlier decisions, dependencies, and incomplete work.

This research suggests that structured, evolving project knowledge can improve consistency without retraining the underlying model.

**Practical takeaway:** Separate three kinds of agent memory:

**Project knowledge:** Architecture, dependencies, conventions.

**Working state:** Current task, decisions, changes, unresolved issues.

**Historical knowledge:** Previous failures, incidents, and successful approaches.

Use deterministic code navigation for relationships and retrieval over engineering history where appropriate. Keep important working state inspectable and versioned.

## 4. Tangent: Most agent testing is still surprisingly shallow

**October 12 IBM listing | ASE 2026 research; preprint first posted August 9**

[Read: Tangent — Testing Practices for LLM-Based Agent Applications](https://research.ibm.com/publications/tangent-an-empirical-study-of-testing-practices-for-llm-based-agent-applications)

**What changed:** Researchers examined **2,572 test methods across 240 modules**, supplementing their analysis with interviews involving 10 experienced industry practitioners.

They identified 23 testing patterns and found that agent testing remains dominated by narrowly scoped unit tests, simplistic inputs, extensive mocking, and relatively shallow assertions.

Complex interactions and nonfunctional requirements receive much less attention.

**Why it matters:** This exposes a gap between how agents are tested and how they actually fail.

An agent may pass isolated tool tests but fail when multiple tools, unexpected responses, changing state, and long-running decisions interact.

**Practical takeaway:** Add fault-injection scenarios to agent evaluation suites.

Test tool failures, malformed responses, permission denials, interrupted sessions, stale context, and unsuccessful recovery attempts.

The important measure is not merely whether the agent eventually completes the task, but whether it **recognizes failures and recovers without violating constraints**.

## 5. REAG: RAG can generate better acceptance tests, not just better answers

**Presented October 14 | ASE 2026 industry research**

[Read: Requirements-Augmented Generation for Trustworthy Acceptance Testing](https://conf.researchr.org/details/ase-2026/ase-2026-industry-showcase/29/Requirements-Augmented-Generation-for-Trustworthy-Acceptance-Testing-of-LLM-Based-Sof)

**What changed:** Researchers introduced REAG, which retrieves requirements, domain knowledge, and user personas to construct context-aware acceptance-test oracles for LLM-based applications.

A confidence-calibrated evaluation process determines whether to accept a result, escalate uncertainty, or abstain.

In an industrial case study, the authors reported **98.8% verdict accuracy** for their calibrated approach and a **31.7% cost-efficiency improvement** over single-judge baselines. These are application-specific results, not general coding-agent performance figures.

**Why it matters:** This connects engineering RAG directly to verification.

Instead of retrieving documentation merely to help an agent write code, the system retrieves authoritative requirements to determine whether the resulting behavior is acceptable.

**Practical takeaway:** Consider a separate acceptance-verification agent with retrieval access to approved requirements, design decisions, and engineering policies.

It should not simply trust the implementation agent's explanation of what was required.

When evidence is insufficient, it should explicitly abstain and request human judgment.

## Priorities for the week ahead

The most interesting combination is **Interaction-as-a-Judge + REAG + Doc2Harness**.

Together, they suggest three distinct verification responsibilities:

| Layer | What gets verified | Mechanism |
|---|---|---|
| Harness | Did the agent operate correctly? | Deterministic behavioral tests |
| Implementation | Does the software work? | Unit, integration, and E2E tests |
| Acceptance | Does the behavior satisfy actual user intent? | Requirements-grounded interactive evaluation |

The distinction is important because each layer can pass while another fails.

### One experiment worth running

For an interaction-heavy web application, select a feature with meaningful user interactions.

Have the implementation agent work against predefined requirements. Then run two independent evaluations: conventional Playwright tests and an interactive agent supplied with the acceptance criteria.

Compare the defects each detects, false positives, verification costs, and human interventions required.

**The central takeaway:** Practical techniques are emerging for separating *agent execution*, *software correctness*, and *user-intent verification*.

That's a stronger foundation for increasing agent autonomy than simply adding more human review checkpoints.

The next useful investment is not necessarily another coding agent. It's a verification system capable of establishing what the agents actually accomplished.
