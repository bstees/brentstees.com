The strongest signal this week is a sharpening distinction between **agent autonomy** and **engineering authority**. The interesting work is increasingly about deciding what agents may do freely, what must be externally represented, and what constitutes proof that the work is actually done.

### 1. MAGE: turn engineering judgment into durable constraints, not repeated prompts

A new August 25 paper, **Model-Based Agentic Software Engineering (MAGE)**, argues that as coding becomes cheap, the scarce resources become engineering intent, abstraction, evidence, and acceptance judgment. Its answer is to externalize the smallest useful representation of those things and give settled decisions real authority through constraints, sensors, validators, and gates. The framework was refined through a longitudinal case and used to explain six independently reported industrial accounts.

**Source:** [Model-Based Agentic Software Engineering](https://arxiv.org/abs/2608.25174)

**What changed:** This goes beyond “give the agent better context.” It distinguishes information the agent should *consider* from engineering obligations it must *obey*.

**Why it matters:** That is a much better model for agentic development than stuffing everything into `AGENTS.md` and hoping the model remembers which statements are mandatory.

**Practical takeaway:** Classify engineering knowledge explicitly:

**context → guidance → invariant → acceptance criterion → enforced gate**

An architectural preference may remain guidance. A security boundary should become a validator. A Definition of Done item should produce evidence before the phase can close.

### 2. Formal verification is becoming surprisingly practical when agents do the proof work

At ICFP on August 27, Microsoft Research presented **Proofs Promptly**, an experience report on agents using a CLI plus the F*/Pulse proof environment. Three experts spent roughly two weeks producing case studies the authors estimate would otherwise require around **six months of manual proof engineering**. The agents implemented verified data structures, translated unverified code while inferring specifications, and refactored existing proofs. Human effort centered on reviewing specifications and occasionally supplying a crucial invariant.

**Source:** [Proofs Promptly: Proof-Oriented Programming with AI Agents](https://doi.org/10.1145/3828709)

**What changed:** Formal methods have traditionally been powerful but too expensive for ordinary development. Agents may alter that cost equation because proof construction is highly iterative, machine-checkable work.

**Why it matters:** This is verification-first engineering taken much further than unit tests: instead of a human inspecting generated code, the machine can verify properties of it.

**Practical takeaway:** Adopting F* is not the immediate requirement. The broader pattern is to **push verification toward mechanisms where correctness can be independently computed**. Property-based tests, mutation testing, schema validation, static analysis, contracts and invariants all move human effort from checking implementation toward deciding *what must be true*.

### 3. Goldman is turning “tribal knowledge” into reusable agent skills

A substantive look at Goldman Sachs' rollout this week describes a common enterprise problem: its roughly 12,000 developers have access to coding agents, but the real challenge is teaching agents how Goldman actually engineers software. The company is codifying internal practices into reusable **skills**, including task-specific guidance such as how a cloud migration should be performed, then refining those skills from observed agent performance.

**Source:** [Goldman's engineers have a new challenge: turning AI agents into firm insiders](https://www.businessinsider.com/goldman-sachs-engineers-ai-marco-argenti-2026-8)

**What changed:** Enterprise agent enablement is progressing from “RAG over organizational documentation” toward **codified executable ways of working**.

**Why it matters:** RAG answers *what does the organization know?* Skills can answer *how is work done here?* Those are different problems, and engineering agents need both.

**Practical takeaway:** Treat repeated human corrections as candidates for promotion:

**conversation correction → documented rule → reusable skill → automated check where possible**

This creates a practical path for steadily decreasing required human intervention without granting blanket autonomy.

### 4. Security research is arguing for an “assurance case,” not a passing test suite

A new evidence-centered survey published August 21 connects software-engineering and software-security research on LLM agents. Its central point is that repository access and execution feedback can improve functional success while still revealing very little about security. Conversely, security scans alone say little about whether software actually works. The authors propose evaluating agent output across functional correctness, security, operational reliability, provenance, and agent authority rather than relying on one benchmark or test result.

**Source:** [Large Language Models at the Intersection of Software Engineering and Software Security](https://arxiv.org/abs/2608.21107)

**What changed:** “Tests pass” is increasingly being treated as **one piece of evidence**, rather than synonymous with “verified.”

**Why it matters:** An agent that writes implementation and tests can easily create a self-consistent but incorrect result.

**Practical takeaway:** Make each completed agentic phase produce a small **evidence bundle**, for example:

requirements satisfied + tests executed + static/security checks + assumptions + unresolved uncertainty + human decisions required.

That is much more scalable than asking a reviewer to reconstruct all of it from the diff.

## The thread connecting all four

This week's material suggests a useful evolution of the human/agent lifecycle:

**Human establishes intent and invariants → system codifies enforceable obligations → agent executes aggressively → independent mechanisms generate evidence → human judges the residual uncertainty.**

That last phrase is the key: **residual uncertainty**.

Human checkpoints should not be defined merely by workflow stage, such as “human reviews after implementation.” A stronger framework asks:

> **What judgment remains that the system cannot currently verify reliably?**

Everything else is a candidate for automation.

This provides a principled way to increase agent eagerness over time without simply increasing autonomy and hoping quality follows.
