This week's best material reinforces something that has been emerging for a while, but with much better evidence now: **the harness around the model is becoming as important as the model itself.** Requirements quality, iteration structure, independent verification, and context management are all showing measurable effects.

### 1. Harness-of-Harness: sustained agent work improves when the *outer loop* controls progress

Published September 1, **Harness-of-Harness (HoH)** wraps existing coding agents in repeated planning → coding → testing cycles. Importantly, it scopes work into small verifiable increments, separates the agent's implementation-time tests from independent evaluation, maintains versioned history, and specifies verifiable outcomes rather than prescribing exactly how the agent must work. Across three different model/harness combinations, the researchers report an average **52.25% relative improvement** over the underlying harness after three iterations; they also ran one experiment for 70+ iterations over multiple days.

**Source:** [Harness-of-Harness: Multi-Day Autonomous Software Development with Continual Improvement](https://arxiv.org/abs/2609.01481)

**Why it matters:** The improvement came without inventing a fundamentally new coding model. The orchestration architecture made existing agents substantially more effective.

**Practical takeaway:** This maps unusually well to the framework you've been developing. Keep each phase **small, independently verifiable, and outcome-constrained**, but allow high agent eagerness *inside* that boundary. Most importantly, don't let the same agent's self-authored tests be the final evidence that its implementation is correct.

### 2. WiseSpec quantifies how much better requirements can improve agent performance

Also published September 1, **WiseSpec** attacks a different part of the pipeline: the requirement itself. Instead of immediately handing a repository task to a coding agent, it constructs richer structured requirements, evaluates their quality using execution feedback, and iteratively refines them before implementation. Across its experiments, this produced an average **13.17% improvement in resolved tasks** over baseline approaches.

**Source:** [WiseSpec: Requirements-Driven Agents for Code Generation](https://arxiv.org/abs/2609.00568)

**Why it matters:** A lot of agent research focuses on better models, tools and prompts. This suggests meaningful gains are available *before the coding agent starts*.

**Practical takeaway:** I'd strengthen your planned phase format from:

**Goal → Definition of Done → execute**

to something closer to:

**Goal → constraints/unknowns → acceptance evidence → Definition of Done → execute**

Then require the agent to challenge ambiguity before implementation. That's not bureaucratic requirements engineering; it's improving the input signal to an increasingly powerful executor.

### 3. GitHub has useful production evidence that optimizing token counts can actually make agents *worse*

On September 2, [GitHub's engineering write-up](https://github.blog/ai-and-ml/github-copilot/how-we-make-ai-coding-more-cost-efficient-without-sacrificing-task-quality/) described experiments optimizing the GitHub Copilot agent harness. One counterintuitive result: shortening individual tool responses sometimes **increased total tokens and execution time**, because the agent later reread files or reran commands to recover missing context. Their successful approach selectively compresses repetitive build/test output while preserving source, diffs and arbitrary command results.

They also cut roughly half of one accumulated agent prompt using a meta-prompting loop — and accidentally caused independent agents to execute sequentially. Offline evaluation missed it; an online experiment caught it. GitHub then added a behavioral regression test before fixing and shipping the optimization.

**Why it matters:** This is basically **software testing applied to the agent harness itself**. Prompts, context filters, tools and orchestration rules have behavior and therefore need regression tests.

**Practical takeaway:** Treat your agent configuration as executable software. When you discover a desirable behavior — *run independent investigations concurrently*, *don't change architecture without approval*, *execute the targeted tests before continuing* — create an eval for it. Then changes to your Markdown instructions, skills or MCP/tool configuration have a test suite.

### 4. FrontierSWE v2 moves evaluation toward the kind of work where agents actually need engineering endurance

The September release of **FrontierSWE v2** expands to 34 extremely long-horizon tasks spanning implementation, performance engineering, scientific computing, visual reasoning and AI research. Agents can work for **up to 20 hours per task**, with five runs per task, and all models run through the same minimal harness so model capability is less confounded by proprietary orchestration.

**Source:** [FrontierSWE v2](https://www.frontierswe.com/blog/v2)

Examples aren't "fix this method." They include reimplementing Git in Zig, decoding speech from MEG data and training a medium-range weather forecasting model.

**Why it matters:** SWE-bench-style issue resolution is becoming insufficient as a proxy for what agents can do. Long-duration work introduces state management, bad early decisions, context degradation, recovery and verification problems that short tasks largely hide.

**Practical takeaway:** When evaluating an agentic IDE or model internally, add at least one **multi-hour realistic engineering task**. Measure not merely whether it finishes, but how often a human must redirect it, how much work gets discarded, and whether its final evidence actually supports its claimed completion.

### The thing I'd experiment with next

HoH + WiseSpec + GitHub's harness findings fit together almost suspiciously well:

**Requirement refinement → bounded phase → eager agent execution → deterministic tests/evidence → independent verification → next phase**

And there's an important distinction emerging between **constraints** and **instructions**.

Tell the agent *what must remain true* and *what evidence constitutes done*. Avoid unnecessarily telling it exactly *how to get there*.

That gives the model room to exploit its growing capability while keeping engineering authority outside the model. For the agentic-development exercise you've been designing, I think this is now a stronger architecture than either conventional pair-programming with AI or open-ended autonomous coding.
