**This week's theme: A plausible result is not the same as a verified one. Check individual requirements, test whether reviews catch real defects, and measure whether a cheaper run still gets the job done.**

This issue looks at requirements that slip through a green test run, review and testing tools that need their own scorecards, and ways to reduce agent cost without losing verified fixes.

## 1. A green subset is not a finished assignment

*November 15 · arXiv preprint*

**Source:** [SWE-CoWork: Benchmarking Coding Agents as Digital Employees in Organizations](https://arxiv.org/html/2611.20218v1#S6)

**What changed:** SWE-CoWork tested agents on 101 assignments where requirements were spread across simulated colleagues and workplace records. The two leading models passed roughly 63% of tests for newly required behavior but completed fewer than 8% of assignments. In a separate analysis of 101 Claude Opus 5.5 trajectories, 255 of 826 requirements the model reported complete failed their tests.

**Why it matters:** Knowing what to build, implementing it, and verifying it are separate steps. Aggregate test pass rates can conceal requirements that were missed altogether.

**Practical takeaway:** In one pilot, record each requirement and its acceptance check. Leave unverified or unresolved items open even if the agent says the task is finished. The study identifies requirement tracking as a research direction; it does not verify that a ledger improves completion.

## 2. Evaluate automated review against defects, not comment count

*November 18 · Vendor field report*

**Source:** [Lessons from building Sashiko, an agentic code review system](https://cloud.google.com/blog/products/application-development/lessons-from-building-sashiko-an-agentic-code-review-system)

**What changed:** Google reports that Sashiko, using Gemini 4 Carbon at high thinking, identified 75.8% of nearly 1,000 retrospectively selected bugs missed by human review. In a separate observational dataset of 21,500 tracked mainline commits, the reported 60-day fix rate was 0.9% for clean reviews and 7.6% following critical warnings. These groups differ, so the rates do not establish causation.

**Why it matters:** A reviewer that catches real defects can be useful even if it does not replace human judgment; a high volume of comments is not evidence that it does.

**Practical takeaway:** Run a reviewer against historical defects and a sample of clean changes. Track useful catches, false positives, and time spent triaging each.

## 3. More tests can help, but translated suites need their own checks

*November 16 · arXiv preprint*

**Source:** [Can Coding Agents Write and Transpile Unit Tests](https://arxiv.org/html/2611.21797v1#S5)

**What changed:** Researchers evaluated test generation across 240 open-source Python, C++, and Rust projects. Generated tests improved aggregate coverage and mutation scores, but quality fell with project size and much of the gain came from writing more tests. In the separate C++-to-Rust translation evaluation, translated suites regressed on about 55% of projects.

**Why it matters:** More generated tests can catch more defects, but passing a translated suite does not establish that it preserves the original suite's behavioral checks.

**Practical takeaway:** Use mutation checks to assess what the new suite catches, and carry a small set of known failures or critical behaviors across the language boundary.

## 4. Measure savings without trading away successful fixes

*November 16 · Microsoft Research report*

**Source:** [TokenEconomizer: Learning from experience to make AI coding agents more efficient](https://www.microsoft.com/en-us/research/blog/tokeneconomizer-learning-from-experience-to-make-ai-coding-agents-more-efficient/)

**What changed:** TokenEconomizer uses prior runs to detect detours and redirect an active coding agent. Microsoft reports 18.4–30.9% lower mean costs across five agent/model combinations on the same 277 SWE-Bench tasks from six repositories, including the controller's own calls. The [released plugin](https://github.com/microsoft/TokenEconomizer#settings) disables micro-skills by default and alerts the developer when a redirect fails.

**Why it matters:** The measured savings apply to this evaluation, not to every repository or default install.

**Practical takeaway:** Compare cost per verified fix, elapsed time, and final pass rate on the same tasks with and without redirects. Track failed redirects separately so time saved is not confused with work abandoned.

## 5. Tie verification to the final commit

*November 16 · Vendor engineering report*

**Source:** [How the Claude Code team thinks about verification](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)

**What changed:** The Claude Code team describes reviews tied to specific commits and a 39-item checklist whose applicable subset is typically three to ten checks. Review instructions come from the base or default branch. Its commit gate can observe or enforce, but permits explained exceptions and lets the next attempt through after two blocks in the same session.

**Why it matters:** A review of one commit does not verify a later commit. And an interactive guardrail with exceptions is not a replacement for an independently enforced release check.

**Practical takeaway:** Start in observe mode and measure the noise. Tie results to the exact commit, record exceptions, and enforce the checks that should never be skipped in protected CI.

## Priorities for the week ahead

Pick one agent-assisted change. Write down what must be true, attach evidence to each requirement, and recheck it at the final commit. For tools that promise faster reviews, cheaper runs, or more tests, count defects caught and fixes verified alongside time and cost.
