This week has one unusually clear theme: **“harness engineering” is graduating from an emerging idea into a recognized engineering discipline.** That matters because it shifts attention from choosing the smartest model toward designing the control system around it.

### 1. Gartner formally identifies Coding Agent Harness Engineering as an emerging discipline

On September 8, Gartner published **Innovation Insight: Coding Agent Harness Engineering**. Its central conclusion is that frontier models and coding agents alone aren't enough to scale an AI-native SDLC; engineering organizations need an explicit harness governing complex multi-step agent workflows.

[Gartner — Coding Agent Harness Engineering](https://www.gartner.com/en/documents/8346017)

**What changed:** Harness engineering has moved beyond papers and practitioner terminology into mainstream engineering-management research.

**Why it matters:** The model becomes one replaceable component. Repository guidance, context selection, tools, permissions, feedback, tests, state and human gates become the durable engineering system.

**Practical takeaway:** Architect agent frameworks so **Codex, Claude Code, Copilot or whatever comes next is an interchangeable executor**. Requirements, lifecycle, evidence and authority should live outside the model.

### 2. A source-code study finds production coding agents aren't actually using vector RAG for code

One of the more surprising findings in **Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents** comes from inspecting roughly four million lines across 11 production harnesses, including Claude Code, Codex CLI, Gemini CLI, Aider and OpenHands.

Across those systems, the researchers found **none retrieving code through vector embeddings**. Deterministic repository exploration dominates instead. Skills are also now slightly more prevalent than MCP in the systems studied: 9/11 versus 8/11.

**Source:** [Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents](https://arxiv.org/abs/2609.00006)

**What changed:** The practical architecture of coding agents is diverging somewhat from the conventional “embed the repository and RAG over it” assumption.

**Why it matters:** Code has unusually rich structure already: paths, symbols, imports, references, git history, tests and dependency relationships. Semantic similarity isn't necessarily the best first retrieval mechanism.

**Practical takeaway:** For engineering RAG, separate **knowledge retrieval** from **code navigation**. Use embeddings where they genuinely help with tickets, design docs, incident history and organizational knowledge. Let agents navigate code through deterministic search, symbols, git and executable tools.

### 3. The strongest harness results suggest the system can learn, not just the model

The earlier **Agentic Harness Engineering** study takes the idea another step: automatically improving the harness itself from observed agent trajectories. Its system records editable harness components, distills enormous trajectories into useful evidence, predicts what each harness modification should improve, and checks that prediction against subsequent runs.

Ten iterations increased Terminal-Bench 2 pass@1 from **69.7% to 77.0%**, versus 71.9% for the human-designed Codex CLI harness. More interestingly, the resulting harness transferred to other model families, improving them by 5.1–10.1 percentage points. Ablations attributed much of the gain to **tools, middleware and long-term memory rather than system-prompt wording**.

**Source:** [Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses](https://arxiv.org/abs/2604.25850)

**What changed:** There's now stronger evidence that accumulated engineering experience can reside in the **harness**, not merely the model or giant instruction file.

**Why it matters:** That makes human corrections potentially compounding assets.

**Practical takeaway:** When a human intervenes in an agent run, classify whether the lesson belongs in:

**instruction → skill → tool → validator → test → workflow constraint**

Moving a lesson farther to the right, when safe, reduces the chance that another agent will need the same human correction.

### 4. A new industry survey exposes a governance gap around agents

Released September 10, Harness's **State of Agent DLC 2026** surveyed 700 engineers, engineering leaders, and technology professionals and found confidence in agent deployment running ahead of the controls organizations have for testing, security and governance. The report specifically highlights the mismatch between nondeterministic agents and delivery controls originally designed for deterministic software.

**Source:** [The State of Agent DLC 2026](https://www.harness.io/state-of-agent-dlc-2026)

**What changed:** Organizations are beginning to distinguish **testing the software an agent produces** from **testing the agentic system producing it**.

**Why it matters:** Application tests can all pass while the development agent itself has behaved incorrectly: accessing something it shouldn't, ignoring an instruction, wasting enormous resources, changing unrelated files or reaching the correct result through an unacceptable process.

**Practical takeaway:** Build two test surfaces:

**Product verification:** *Is the resulting software correct?*

**Agent verification:** *Did the agent operate within its authority and engineering constraints?*

Those should eventually be separate suites.

### 5. Andrew Ng's new workflow puts the human precisely where verification stops being objective

Andrew Ng published updated coding-agent guidance last week emphasizing specifications, iterative planning, tests and calibrated autonomy rather than simply leaving increasingly capable agents unattended. The important principle is that autonomy should expand according to **what engineers can independently verify**.

**Source:** [AI Engineering Skills Map: Using coding agents](https://www.linkedin.com/pulse/ai-engineering-skills-map-using-coding-agents-andrew-ng-h8yxc/)

**What changed:** Human-in-the-loop guidance is becoming less about frequent supervision and more about deliberately placing humans at **judgment boundaries**.

**Why it matters:** That's a much more scalable definition of HITL. A human watching an agent execute deterministic work isn't adding much value.

**Practical takeaway:** At every human checkpoint, identify the judgment that cannot yet be reliably automated:

> **What judgment requires a human because it cannot yet be reliably automated?**

Checkpoints without a clear answer should be eliminated.

## The important synthesis

Items **2 and 3** are especially consequential.

They suggest that an effective agentic engineering environment may ultimately contain three different kinds of organizational knowledge:

**Docs/RAG** — *What is known?*
**Skills/instructions** — *How is the work normally done?*
**Executable harness controls** — *What must be true?*

And there's a hierarchy hiding inside that:

**prose < skill < executable verification**

When an engineering lesson becomes stable enough, move it down that chain.

The result is considerably more powerful than an ever-growing `AGENTS.md`: **an engineering system that gradually converts human judgment into reusable organizational capability while deliberately retaining humans for the decisions that remain genuinely judgmental.**
