**This week's theme: Agentic systems become more credible when completion claims are checked by mechanisms outside the agent. This week’s strongest work paired human-approved specifications with deterministic controls, longer evaluation horizons, and adversarial verification.**

A DeepMind case study applied agent-generated formal proof to deployed cryptographic code, while OpenAI described a control-plane architecture for persistent internal agents. New preprints examined long-horizon infrastructure work and security alerts that vanish without removing a vulnerability; GitHub added policy-manageable rollout for AI Scan.

## 1. Formal proof moves the human gate to the specification

*November 10 · Vendor formal-verification case study*

**Source:** [Introducing AlphaProof Code: a breakthrough in verifying complex software at depth](https://deepmind.google/blog/introducing-alphaproof-code/)

**What changed:** Google DeepMind reports that AlphaProof Code helped formally verify key security properties of Signal’s compiled cryptographic implementation. Human experts reviewed every formal specification, agents generated more than six million lines of Lean proof, and Lean checked the proofs. Two previously fixed bugs were reintroduced as negative controls and identified. This is a vendor-reported case study over a defined implementation and trusted formalization; it does not establish coverage of every Signal feature or execution case.

**Why it matters:** The case demonstrates one division of labor for high-consequence verification: people approve what must hold, agents perform extensive proof work, and a separate proof kernel checks the result.

**Practical takeaway:** Pilot formal verification on one narrow invariant, require human approval of the specification, record the trusted assumptions, and include a known-bad version as a negative control.

## 2. Persistent agents need controls outside the harness

*November 12 · Vendor engineering report*

**Source:** [Securing persistent agents like OpenClaw at OpenAI](https://developers.openai.com/blog/securing-persistent-agents-like-openclaw-at-openai)

**What changed:** OpenAI described an internal pilot architecture that treats the persistent-agent harness as untrusted while keeping policy and credential enforcement in a trusted gateway and control plane. Other reported layers include sandbox restrictions, credential brokerage, model-based review, distinct agent identities, and centralized observability. OpenAI reports operating more than 500 internal agents, but the post is vendor experience rather than an independent comparative security evaluation.

**Why it matters:** Long-lived agents accumulate opportunities for stale context, permission misuse, and hidden failure. Controls outside the harness remain enforceable when model judgment is wrong.

**Practical takeaway:** Diagram one persistent-agent path and verify where network access, secrets, identity, writes, approvals, and escalation are enforced outside the model loop.

## 3. Long-horizon evaluations change what completion means

*November 9 · arXiv preprint and author-built benchmark*

**Source:** [Infrathon: Benchmarking Language Agents for Real-World, Long-Horizon AI Infra Optimization](https://arxiv.org/abs/2611.11995)

**What changed:** Infrathon introduces 25 AI-infrastructure optimization tasks and evaluates six models across 150 runs with budgets of up to 24 hours, totaling more than 10,000 GPU-hours. The authors report that 135 runs improved their best private-test score during the second half of the allotted time; trajectory analysis also found instruction violations, unreliable testing, and premature completion. Results are specific to the author-built tasks, H100 environments, differing agent harnesses, and a single run per task-model pair rather than repeated-seed estimates.

**Why it matters:** Short evaluations and agent completion messages can miss both late gains and late failure modes. Long-running software-engineering work needs timeline-aware verification and acceptance evidence.

**Practical takeaway:** For one long-running workflow, score private checks at fixed intervals, record rule violations and invalid tests, and run an external stop hook after the agent declares completion.

## 4. A vanished security alert is not a repair certificate

*November 12 · Empirical software-security preprint*

**Source:** [Preserve the Vulnerability, Break the Alert: Testing the Robustness of CodeQL Taint Tracking with Natural Rewrites](https://arxiv.org/abs/2611.17123)

**What changed:** Researchers started with 172 CodeQL-detected JavaScript flows from real npm vulnerabilities and used an alert-aware language model to generate three plausible, vulnerability-preserving rewrites per flow. After analyzer checks and manual audit, at least one rewrite silenced the alert for 26.2% of flows while preserving the flaw; a benign-refactoring baseline silenced none. The study is limited to selected JavaScript taint flows, CodeQL’s modeling boundaries, and a generator explicitly shown the alert.

**Why it matters:** An absent static-analysis alert is evidence about the analyzer’s current view, not independent proof that the underlying vulnerability was removed.

**Practical takeaway:** Preserve an exploit reproduction, security invariant, or mutation test across agent refactors instead of accepting alert disappearance as the sole repair criterion.

## 5. AI Scan rollout becomes policy-manageable, not self-executing

*November 13 · Public-preview product changelog*

**Source:** [Manage AI Scan for repositories using the REST API](https://github.blog/changelog/2026-11-13-manage-ai-scan-for-repositories-using-the-rest-api/)

**What changed:** GitHub added organization- and repository-level REST controls for the `repository_scan` setting, allowing AI Scan rollout through scripts or infrastructure as code. The feature remains in public preview. Enabling it does not run a scan; a user with write access must start scans on demand, each scan consumes Code Security AI credits, and GitHub Enterprise Server is unsupported.

**Why it matters:** Security-tool governance can now be managed as versioned policy, but configured state remains separate from execution and review evidence.

**Practical takeaway:** Pilot the setting on a small repository cohort, manage desired state as code, and test scan invocation, alert handling, credit use, and rollback as separate acceptance checks.

## Priorities for the week ahead

Engineering teams can tighten the boundary between a claim and its verifier: approve the specification, name the independent oracle, record trusted assumptions, and test at least one known-bad case. Persistent and long-running agents also need enforceable identity, access, stop, and evidence controls outside the model loop.
